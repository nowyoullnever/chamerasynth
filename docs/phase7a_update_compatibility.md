# Phase 7A — update compatibility and resource-only boundary

## What the offline candidate changes

The local BEEP experiment changes only source file range `0x121e00..0x122deb` inclusive. It preserves the 0x200-byte alignment, the 4,096-byte allocation, the 20-byte `0xff` trailing padding, every resource-index byte, and source header bytes `0x000000..0x0001ff`. Its manifest contains no metadata update.

This is an exact source-diff statement. It is not a statement that any updater accepts the candidate.

## Phase 4 updater evidence reused

Phase 4 statically recovered an SD update discovery path and SPI erase/program/verify helpers: 64 KiB erase opcode `0xd8`, 256-byte program opcode `0x02`, and verify-read opcode `0x03`. That evidence does not establish the accepted image container, image-length policy, signing/checksum policy, target address, capacity, RAM execution behavior, boot recovery, or a safe power-loss procedure for this stock image.

The BEEP range is below the previously observed raw-image boundary questions, but no static proof says that a source image with this range changed is a valid SD update input. No update package is generated by Phase 7A.

## Compatibility verdict

| Question | Result |

The experimental copy remains `analysis-only-copy` and `flash_ready: false`. It must stay private and ignored; the original source, candidate image, and generated WAV are excluded from Git and the Phase 7A result archive.
